## Куча (занятие 8)

`Heap.Minimum` — минимум-куча на массиве с нульиндексной адресацией:
parent(i) = (i−1)/2, left(i) = 2i+1, right(i) = 2i+2.
Вставка и извлечение — O(log n), чтение минимума — O(1).
Пирамидальная сортировка поверх той же идеи лежит в `05-sorting-search`.

## Деревья поиска (занятие 12)

| Реализация | Гарантия высоты |
|---|---|
| `BinarySearchTree` | нет: отсортированный вход вырождает дерево в список |
| `AVL` | разница высот поддеревьев не больше единицы |
| `RBT` | высота не больше 2·log(n+1) |

`Main` в пакете `tree.search` печатает число шагов поиска — видно, как балансировка спасает
от вырождения.

### Сравнение поиска в BST, AVL и RBT

`tree.search.Main` строит три дерева на одинаковых ключах 1–9 и выполняет
одинаковые запросы: 8 есть в дереве, 150 отсутствует. Сначала ключи вставляются
в смешанном порядке, затем — по возрастанию. Перед каждым запросом вызывается
`counter.reset()`, поэтому предыдущий поиск не влияет на следующий замер.
Программа также проверяет ответы относительно исходного списка ключей.

Один шаг поиска — посещение текущей позиции дерева. Посещение отсутствующего
ребёнка (`null`, в лекции NIL) тоже считается: именно в этой позиции поиск
устанавливает, что ключ отсутствует. Пустое дерево требует один такой шаг.
Это число посещений, а не число вызовов `compareTo` и не время выполнения.

```sh
mvn -pl 08-heap-trees -am verify
java -cp 08-heap-trees/target/classes:00-commons/target/classes \
  ru.mifi.practice.vol6.tree.search.Main
```

| Ввод | Дерево | Поиск 8 | Поиск 150 |
|---|---|---:|---:|
| Смешанный `[5,2,8,1,3,6,9,4,7]` | BST, AVL, RBT | 2 | 4 |
| Отсортированный `[1,2,3,4,5,6,7,8,9]` | BST | 8 | 10 |
| Тот же отсортированный | AVL | 3 | 5 |
| Тот же отсортированный | RBT | 3 | 5 |

На отсортированном входе BST вытянулось в цепочку. AVL и RBT восстановили
баланс и сократили путь поиска. Равные числа в этом примере не означают,
что AVL и RBT всегда имеют одинаковую форму или одинаковую цену поиска.

### Counter для вставки и удаления

У всех трёх реализаций есть `add(value, counter)` и `delete(value, counter)`
через общий `BinaryTree`. Вызовы `add(value)` и `delete(value)` сохранены.
Счётчик передаётся на вызов, накапливает шаги и сбрасывается только явным
`reset()` — можно измерить одну операцию или целую последовательность.

По решению R2653 один учебный шаг — обработка текущей позиции дерева:

- Нисходящий обход вставки/удаления считает каждый узел и достигнутую пустую
  позицию, как поиск. При найденном дубликате или удаляемом узле пустой
  позиции нет. Поиск преемника считает каждый посещённый узел.
- BST после спуска не балансируется. Если удаление преемника повторно
  проходит уже посещённые узлы, эти новые посещения тоже считаются.
- AVL считает ещё один шаг на каждый проход обновления высоты и проверки
  баланса при возврате из рекурсии. Повороты входят в этот проход.
- RBT считает каждый проход восстановления цвета/баланса и завершающую
  обработку корня после вставки либо замены после удаления чёрного узла.
  Завершающая пустая замена тоже считается. Повороты и перекраски внутри
  прохода не прибавляются отдельно.

Это шаги обхода и восстановления, а не все инструкции JVM. Цена одного
такого шага может различаться; `Main` сравнивает именно поиск, у которого
правило подсчёта полностью одинаково. Существующий `Counter` хранит `int`.

Например, отдельные вставки 10, 5, 1 дают для BST числа 1, 2, 3;
для AVL — 1, 3, 5; для RBT — 2, 3, 5. Перед каждой вставкой счётчик
сброшен. У первого узла RBT два шага: пустая позиция и обработка корня.

### Примеры красно-чёрного дерева из лекции

```sh
java -cp 08-heap-trees/target/classes:00-commons/target/classes \
  ru.mifi.practice.vol6.tree.search.RBTDemo
```

`RBTDemo` после каждой вставки печатает дерево, цвета и число шагов.
`Ч` означает чёрный узел, `К` — красный, `[левый, правый]` — детей,
`NIL` — пустую позицию. Последовательности 10, 5, 1, 15 и 10, 5, 7
показывают поворот, перекраску и случай треугольника. Отдельно удаляется
чёрный лист 5 из дерева, построенного вставками 10, 5, 15, 20.
Итог — чёрный корень 15 с чёрными детьми 10 и 20; удаление занимает
4 шага (2 посещения и 2 шага восстановления). Поиск 20 затем требует
2 шага, поиск удалённого 5 — 3, включая конечный NIL.

## Код Хаффмана для файла (занятие 12)

`tree.huffman.Main` показывает коды символов строки. `tree.huffman.HuffmanFile` применяет
то же дерево к байтам файла. На JDK 17 выполните из корня репозитория:

```sh
mvn -pl 08-heap-trees -am verify
work=$(mktemp -d)
printf 'BOOBS BOOM' > "$work/example.txt"
codec=ru.mifi.practice.vol6.tree.huffman.HuffmanFile
java -cp 08-heap-trees/target/classes "$codec" compress "$work/example.txt" "$work/example.huf"
java -cp 08-heap-trees/target/classes "$codec" decompress "$work/example.huf" "$work/restored.txt"
cmp "$work/example.txt" "$work/restored.txt"
wc -c "$work/example.txt" "$work/example.huf" "$work/restored.txt"
```

`cmp` завершается успешно при полном совпадении. Ожидаемые размеры — 10, 34 и 10 байт.
Коды занимают 21 бит, то есть три байта после упаковки и дополнения нулями справа.
Заголовок занимает ещё 31 байт. Попробуйте другой короткий текст и сравните полные размеры.

Заголовок HUF1 состоит из четырёх байтов сигнатуры, двух байтов числа разных значений
и пар «байт, четырёхбайтовая частота». Декодер строит то же дерево. При равных весах
сначала выбирается лист, затем узел с меньшим минимальным байтом в поддереве.
Исходная длина равна сумме частот. Вход и восстановленный файл ограничены 65 536 байтами
исходных данных. Команды создают новые выходные файлы.

ZIP хранит записи файлов и каталог. Один из методов сжатия записей, DEFLATE, сочетает
ссылки на повторы с кодами Хаффмана. HUF1 хранит один поток байтов в собственном формате.

## Формат файла дерева

Построчно `владелец:{левый, правый}`. Пример в `src/main/resources/standard.tree`.

## B-дерево и страницы индекса (занятие 12)

`tree.search.BTree` хранит целые ключи. В учебном дереве минимальной степени 2 узел
вмещает до трёх ключей. Перед спуском в полный узел алгоритм делит его на два и
поднимает средний ключ к родителю. Полный корень получает нового родителя.
Повторная вставка возвращает `false` и сохраняет форму дерева.

1. На бумаге вставьте по очереди 10, 20, 30, 40, 50, 60. Перед вставкой 40
   поднимите 20 в новый корень, перед вставкой 60 перенесите в корень ключ 40.
2. Найдите 30, 35 и 40. Для каждого ключа запишите ответ и число посещённых узлов.
3. Выполните команды из корня репозитория на JDK 17 и сравните вывод с рисунком.

```sh
mvn -version
mvn -pl 08-heap-trees -am verify
java -cp 08-heap-trees/target/classes ru.mifi.practice.vol6.tree.search.BTreeDemo
```

Ожидаемый корень — `[20, 40]`. Его потомки слева направо — `[10]`, `[30]`,
`[50, 60]`. Ключ 30 найден за два посещения, ключ 35 отсутствует после двух
посещений, ключ 40 найден за одно. Этот счётчик показывает посещения узлов в
памяти. В модели лекции каждое посещение соответствует обращению к странице
индекса, которая может быть уже в кэше.

Для самопроверки добавьте метод в `BTreeTest`. Подберите свою последовательность
вставок, при которой разделится полный внутренний узел ниже корня. Для ориентира
после вставки 1–17 по порядку корень содержит `[4, 8, 12]`. Ключ 12 поднимается
при вставке 17. Сверьте форму до и после выбранного расщепления через `snapshot()`.
Проверьте после каждой вставки порядок ключей, диапазоны потомков, число ключей
в узлах, число потомков и одинаковую глубину листьев. Запустите Maven ещё раз.
